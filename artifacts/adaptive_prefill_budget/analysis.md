预算公式：

```python
min(
    self.prefill_budget,
    self.protected_prefill_tokens,
    max(self.min_chunk_tokens,
        self.target_batch_tokens - len(self.decode_manager.running_reqs)),
)
```

关闭开关时返回原来的固定保护预算。两个阶段都有请求且连续Decode达到K时才计算动态预算；没有活跃Decode时仍使用正常预算。计算过程不做前缀探测、树修改、引用计数或资源分配。`inflight_tokens`继续承担原有KV预留职责。

ChunkedReq复用已分配的Table槽位、缓存Handle与真实进度，下一次可以使用不同预算；KV完整需求检查、LPM排序、有效轮次Aging、FCFS退化、提交计数与完成/Abort释放流程均复用现有实现。小预算不跳过资源检查，也不强制按页大小取整。

## Benchmark设置

环境为AMD Ryzen 7 5800H、WSL2、Python3.12.14、Torch2.9.1+cu128，1个Torch线程。使用真实Scheduler、Prefill/DecodeManager、RadixCache、TableManager、物理页分配和结果回收；CPU Engine只模拟进度与输出，不执行模型、Attention、采样或CUDA Graph。

计时覆盖阶段选择和准入，包含实验记录开销，不含物理页准备和模拟Forward。请求按固定Batch序号到达；随机种子31723，每组5次重复，打乱运行顺序，重复运行的非计时指标必须一致。记录的等待/输出间隔都是Batch数，不能换算成真实GPU延迟。

主实验固定K=16、正常预算8192、保护上限256，初始Decode负载16/64/128/192，目标128/256/512，下限32/64/128。7种负载 × 4种Decode负载 ×（1组固定预算+9组自适应参数）×5重复 = **1400次运行**。

补充实验使用LPM-Aging、N=8、page_size=4、初始Decode16/192、目标256、下限64，7种负载 ×2种负载 ×2种预算模式 ×5重复 = **140次运行**。

交错完成实验使用初始Decode16/192、目标256、下限64、长/混合Prompt两种负载，2×2×2×5 = **40次运行**。

**1580次运行全部排空**，通过表槽归还/唯一性、非根缓存引用归零、protected_size=0、物理页总量和唯一性检查。标准Prefill-only负载强制初始Decode为0，表中的`initial_decode_load`是实验参数；其实际最大活跃Decode数为0，无保护预算计算。

## 主实验结果

以下自适应参数为目标256、最低64，与固定预算256对照：

| 负载 | 初始Decode | 固定/动态保护预算 | 固定/动态Chunk批数 | 首次Prefill等待P95（固定/动态，批） | Prefill完成等待P95（固定/动态，批） |
|---|---:|---|---|---|---|
| 短Prompt | 16 | 256 / 240 | 0 / 0 | 16 / 16 | 16 / 16 |
| 短Prompt | 192 | 256 / 64 | 0 / 0 | 16 / 16 | 16 / 16 |
| 长Prompt | 16 | 256 / 240 | 9 / 10 | 145 / 145 | 145 / 145 |
| 长Prompt | 192 | 256 / 64 | 9 / 10 | 145 / 145 | 145 / 146 |
| 混合冷热 | 16 | 256 / 240 | 7 / 7 | 131 / 131 | 132 / 132 |
| 混合冷热 | 192 | 256 / 64 | 7 / 8 | 131 / 133 | 132 / 133 |

已验证保护预算能随Decode负载缩小，但小预算增加了部分Chunk批次和等待。在这些负载中，初始Decode的最大输出批间隔均为2，未观察到批间隔改善；实际GPU中一次较小Prefill是否减少ITL仍需测量。

混合高负载的CPU调度中位数，固定约16.54µs，自适应约18.09µs。该计时包含调度、准入、实验记录和不同Batch组成，不能把差额全部归因于预算公式。完整P95和运行间范围保存在JSON中。

长Prompt全部排空后的计算量均为32768Token；混合负载均为9239Token并复用1472Token缓存。缩小预算改变分块和交错方式，不减少请求的总计算需求。短Prompt共32个新增计算Token，小于最低预算64，因此多个不同预算下的Batch轨迹相同；预算利用率是逻辑额度填充比例，不是GPU利用率。

目标512在当前实验中始终命中保护上限256，行为指标与固定预算一致。目标128、下限128时始终使用128，说明下限和上限都可能使自适应退化为常量。

LPM-Aging/page_size=4的高负载混合场景，固定/动态首次等待P95均为130批，完成等待为130/132批，Chunk批数为7/8。补充结果用于组合兼容验证，不把同时改变内部策略和页大小的结果归因于某一项独立性能提升。

## 交错完成：同一次运行中的预算变化

初始192个Decode请求、混合负载的自适应保护序列为：

```text
活跃Decode：192 → 192 → 192 → 186 → 139 → 92  → 45
保护预算： 64  → 64  → 64  → 70  → 117 → 164 → 211
```

初始16个Decode的对应预算从240逐渐增加到252。结果直接验证预算并非初始化后固定，而是在每次保护时读取当前活跃数量重新计算。高负载混合请求的首次等待P95仍为固定131批、自适应133批，不能声称自动改善所有请求的排队公平性。

## 资源不足与限制

KV/Table紧张场景，固定与动态均发生111次整批保护尝试失败，继续Decode直到资源允许准入。更小的计算预算没有绕过完整需求检查或消除资源等待。连续Decode达到K只是优先尝试的条件，不能保证资源受限时获得服务。

当前没有本地模型权重，因此未执行真实GPU TTFT、ITL/TPOT、吞吐或显存峰值实验，也未执行多GPU TP运行。活跃请求数只是负载代理；不同上下文长度、后端和GPU下相同请求数可能有不同耗时。本实现不包含混合Prefill/Decode Batch、按实际耗时反馈调整预算、KV抢占或重算。

后续应固定真实请求到达时间和采样配置，分别测量normal/overlap下的TTFT、ITL尾延迟、吞吐和显存，选择适合模型的目标/下限。对长请求或新请求等待恶化的情况，应同时观察Chunk续算优先和有效Aging轮次，不能仅追求更小预算。
